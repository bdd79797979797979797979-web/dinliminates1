## Executive result

The CP704 product snapshot is preserved and deployable as a Vercel preview, but the app is **not yet launch-ready**.

The core Meal experience is structurally strong. The Restaurant experience has two current UI gaps that directly affect requested functionality: the Restaurant Search opener is missing from the HTML, and the Open / All status filter controls are missing. The release/QA plumbing is also materially stale and is not a trustworthy launch gate.

## P1 / launch-significant findings

### 1. Restaurant Search opener is missing
`app.js` has `renderRestaurantSearchControl()` and `bindRestaurantTools()`, both of which expect a DOM element with id `restaurantSearch`.
The current `index.html` contains `restaurantSearchBox` and `restaurantQuery`, but **no `restaurantSearch` element**.

Result: the restaurant-search input cannot be reliably opened from the current UI.

### 2. Restaurant Open / All controls are missing
The current Restaurant HTML contains no `hoursToggle` and no Open/All filter buttons.
The app can calculate open/closed/unknown state, but `restaurantPoolBase()` does not expose an Open-only versus All user choice.

Result: the requested Open / All behavior is not currently available in the live UI.

### 3. Vercel release API is broken in the protected CP704 code
Current `api/release.js` contains:
`require('../release.json')`
but the repository root does not contain `release.json`.
The active release file is `app-release.json`.

Result: `/api/release` is expected to fail on invocation, which directly affects hosted release/diagnosis verification.

### 4. App Diagnosis is hardcoded to CP701 / Build 701
Diagnosis code still expects:
- Build 701
- CP701
- branch `cp701-app-diagnosis-refresh`

Current release metadata is Build 704 / CP704.

Result: Diagnosis can report a false release mismatch even when the current app metadata is correct.

### 5. The primary CI/release gate is stale
`qa/clean-static-qa.js`, `qa/browser-smoke.mjs`, `qa/hosted-smoke.mjs`, `qa/iphone-optimization-smoke.mjs`, `qa/netlify-preview-smoke.mjs`, and related workflows still contain old Build 197/CP487 assumptions, obsolete selectors, or old preview URLs.
Several scripts still read the nonexistent `release.json`.

Result: a green run from the current pipeline would not be a trustworthy CP704 launch certification.

### 6. Restaurant provider timeouts are a demonstrated runtime issue
The Vercel runtime history contains 22 timeout errors in restaurant/photo routes.
The current restaurant API has a 12-second search budget, but `withinBudget()` uses `Promise.race()` without necessarily aborting the underlying provider promise.

Result: the UI may stop waiting while external provider work continues. A stronger master AbortSignal / cancellation strategy should be used for the launch-grade search path.

## P2 / important hardening

### 7. Server-side redirect validation
The restaurant-photo/web discovery layer validates the initial URL but follows redirects without a consistent final-destination network/host revalidation policy.

Result: defense-in-depth SSRF exposure remains possible through redirect chains.

### 8. Service-worker shell cache naming is stale
`sw.js` still uses `dinliminate-shell-v668` while the current app is Build 704 and app.js query v673.

Result: cache governance is harder to reason about and should be versioned consistently for deterministic updates.

### 9. Offline build fallback is one build behind
Current `app.js` fallback is `APP_BUILD='703'` while `app-release.json` is Build 704.

Result: a failed release-metadata fetch can show the wrong build in offline/degraded conditions.

### 10. Restaurant card utility touch targets are small
Choose / Details / Website utilities on Restaurant cards are reduced by later CSS overrides to roughly 32–36px on narrower phone layouts.

Result: these controls are usable but below the conventional 44px touch target used elsewhere in the app.

### 11. Visual regression coverage is too narrow
The stored visual baseline only covers Restaurant start at 393×852.
It does not cover Home, the new CP704 Dine In/Dine Out imagery, Meal swipe, Restaurant swipe, Winner, Details, Notes, History, Settings, or Share/Add-to-Phone states.

### 12. Current Home tagline does not match the selected product direction
Current source still shows:
`Swipe. Dinliminate. Enjoy.`

The more recent direction established for the app was:
`Beautifully swipe until it’s revealed.`

This is a product-copy consistency issue, not a runtime defect.

### 13. Food-image QA has drifted from the current catalog
The 116-item food-image smoke is current about catalog count, but several hardcoded image URL assertions no longer match the current images, including the present Tacos, Fajitas/stir-fry-id, Meatloaf, Buttermilk & Cornbread, Beef Stroganoff, Lasagna, Grilled Salmon, Homemade Pizza, and White Fish assets.

Result: the image QA can fail because the test contract is stale even when the current catalog is intentionally using newer images.

### 14. Release documentation outside the primary files is stale
`CHECKPOINT.md`, `SAVEPOINTS.md`, `IMAGE-SOURCES.md`, and `qa/RELEASE-GATE.md` still lead with historical Build 197/CP487 or earlier release identity.
The current primary release files are correctly aligned to CP704.

### 15. Share fallback has an inline handler
The Share modal creates an input with inline `onclick="this.select()"`.
The Vercel CSP declares `script-src 'self'` and does not allow unsafe inline script.

Result: the convenience click-to-select behavior is not CSP-aligned. The explicit Copy button remains separately bound in JavaScript.

### 16. Repository has no package manifest
There is no current root `package.json`/lockfile in the inspected repository.
The QA workflows install Playwright/PNG tooling ad hoc with `npm install --no-save`.

Result: runtime is simple, but QA dependency reproducibility is weaker than it should be for a launch pipeline.

## P3 / cleanup findings

### 17. Custom meal deletion repeats note cleanup
The custom meal delete path removes the same food note key and saves notes twice.

No user-visible failure is expected; this is cleanup.

### 18. History calendar X is ambiguous on multi-entry days
A day with several decisions exposes an X tied to only the first entry in the calendar cell.

The list/detail views still expose the saved entries; this is primarily a UX clarity issue.

### 19. CSS has historical selector debt
The stylesheet retains obsolete selectors and multiple override layers from older UI iterations, including old `#iphoneHelp` rules after the Home footer moved to icon-only Add/Share controls.

Result: higher maintenance and regression risk.

### 20. Historical workflows remain active/configured enough to confuse release ownership
The repository contains many CP643–CP656-era workflows plus old hosted preview triggers.
These should be archived/disabled or consolidated once the new launch pipeline is authoritative.

## Recommended fix order

1. Repair `api/release.js` to use `app-release.json`, then make App Diagnosis dynamic against the current release metadata.
2. Restore a visible Restaurant Search opener and implement the requested Open / All filter.
3. Replace the obsolete QA/release gate with one authoritative CP704+ pipeline and retire old workflow triggers.
4. Make restaurant search deadlines abortable, not just race-based.
5. Harden redirect/final-destination validation for restaurant-photo/web discovery.
6. Refresh image QA contracts to the current 116-food catalog and current image URLs.
7. Normalize service-worker/cache versioning and update the offline APP_BUILD fallback.
8. Expand visual/phone regression coverage and certify on a physical iPhone.
9. Clean secondary docs/workflows and minor CSS/code debt.
